# designer evals

Regression suite for `designer`. Built with the `skill-creator` eval flow
(smoke-sized: one fixture, one prompt; N=1 per lane — directional, not
statistical).

The committed test case, prompt, and assertions live in `evals.json`. The
fixture is generated by `setup_fixtures.sh`, not committed. The first recorded
run (new skill) is kept in `examples/recorded-run.html` and validated by the
setup script against every assertion, so the fixture cannot silently drift away
from a known-passing output.

## Setup

```sh
config/skills/designer/evals/setup_fixtures.sh [target-dir]
# default target: /tmp/opencode/designer-evals
```

Produces:

| Path | Use |
|---|---|
| `eval-0-settings-wireframe/` | pristine fixture (docs site + declared authority + gate) |
| `with_new/` | copy to run with the current/deployed `designer` skill |
| `with_old/` | copy to run with `baselines/old-SKILL.md` (the version being compared) |
| `.control/pre.sha` | source checksums for the no-implementation-edits assertion |

## Running

Per case, spawn two subagents with the same prompt from `evals.json`:

1. **with_skill** — have it load the current `designer` skill (or read the
   deployed `SKILL.md` and treat it as authoritative).
2. **baseline** — same prompt, but point it at `baselines/old-SKILL.md`.

Each subagent works only inside its own fixture copy (`with_new/` or
`with_old/`) and writes artifacts into the fixture's `design/` directory.

Grade mechanically where possible; spawn a grader (skill-creator
`agents/grader.md`) for the rest. For each run, produce `grading.json` in the
`text` / `passed` / `evidence` shape per assertion, plus `summary.pass_rate`.
Then aggregate and view:

```sh
cd ~/.agents/skills/skill-creator
python -m scripts.aggregate_benchmark <workspace>/iteration-N --skill-name designer
python eval-viewer/generate_review.py <workspace>/iteration-N \
  --skill-name designer \
  --benchmark <workspace>/iteration-N/benchmark.json \
  --static review.html
```

## Reading results

Mapping assertions to checks (eval-0):

1. Authority + gate follow-through — lane reports the real gate command and a
   passing run; artifacts land in `design/`.
2. Token values — exact-match grep against `assets/tokens.css` values.
3. Void states — grep for explicit state sections/panels, not mere mentions.
   The old skill produced error/hover/focus/disabled but no
   empty/loading/partial/long-content — the intended discriminator.
4. Interaction matrix — default/hover/focus-visible/disabled plus one of
   active/loading/error/empty/long-content.
5. Gate — `bash scripts/check-wireframes.sh` exit 0 quoted.
6. Handoff contract — the old skill has none; absent there, present with the
   new skill.
7. No implementation edits — `sha256sum -c .control/pre.sha` in the run copy;
   both lanes should pass (control).
8. Graph vocabulary — cites `design-graph` / `Surface<C,V,N>` / void states.

Measured results (2026-09-11, one run per lane, inline verbatim skill text):

| Assertion | new | old |
|---|---|---|
| 1 authority/gate | pass | pass |
| 2 tokens | pass | pass |
| 3 void states | pass | **fail** (no empty/loading/partial/long-content) |
| 4 matrix | pass | pass |
| 5 gate exit 0 | pass | pass |
| 6 handoff contract | pass | **fail** (no contract) |
| 7 no impl edits | pass | pass |
| 8 graph vocabulary | pass | **fail** |

First run: 8/8 new vs 5/8 old (assertion 4 regraded pass-for-old on the rerun —
it carries hover/focus/disabled/error). No-hint rerun (eval-1): both lanes
discover the authority, so discovery does not discriminate; void states and
handoff still do.
